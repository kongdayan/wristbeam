# WristBeam component review — 2026-10-27

## Scope and acceptance

The user requested another pass over every button and component after the integrated-settings beta. Settings stay in the main window. This is an explicit product choice; macOS's conventional separate Settings window is not being reinstated.

Baseline: `30ce849`, installed public `v0.3.11-beta.3`. The baseline inventory contains 327 control construction sites across 22 SwiftUI files. A construction site can generate many controls through `ForEach`; this is not a claim that 327 runtime states were exercised. AppKit window chrome and application menus are reviewed separately. No private account, watch, location, health values, or FIT data belong in this record or the fixtures.

## Review decisions before implementation

| Area | Finding | Decision |
| --- | --- | --- |
| Window | Installed app exposes native close/minimize/zoom accessibility elements but the observed screenshot lacks visible traffic lights. Prior snapshots captured only the hosting view. A full-screen cause has not been proved. | Share the production native window factory with CI; use a visible, opaque native title bar, explicit unified toolbar and primary full-screen capability; add standard Window menu commands and complete-frame captures. Do not draw imitation traffic lights. |
| Navigation | Expanding seven settings destinations into the same scrolling list can scroll the five primary destinations out of sight. | Keep primary navigation above the independently scrolling settings destinations. Keep Command-comma, main-window routing, selection and scroll restoration. Remove the redundant sidebar Quit button; Quit remains in the application menu. |
| Settings | The default language picker has an ambiguous automatic presentation; three-option segmented controls compete for width; the fixed 45-point percentage label wraps at 160%. | Use explicit native popup menus for stored finite preferences; keep the compact/detailed mode segment. Let the percentage use its intrinsic width; label the actual slider and expose its percentage value. Stack constrained rows and align stacked controls to the leading edge. |
| Actions | Global large controls and fixed 40-point custom buttons overpower normal desktop forms; several pages use a second bordered style. | Regular actions: minimum 32 points, compact 28, explicitly large actions 40; action radius 7, card radius 18. Unify action appearance while preserving native menus, input fields, checkboxes, switches and date pickers. Destructive roles use red; focus and reduced-motion behavior remain. These dimensions are design judgments, not HIG mandates. |
| Selection | The custom checkbox grid acts like buttons to assistive technology; group mixed state is visual only. | Preserve full-cell click targets, supply native checkbox accessibility representation and announce mixed selection. Row/disclosure controls retain a quiet hover and focus treatment. |
| Responsive actions | Weather search/location, update actions, installed-face actions, developer actions, share footer and chart date controls use rigid horizontal groups. | Let independent actions wrap. Give search entry its own readable row. Preserve paired date navigation and field semantics. Remove fixed card heights where growing text needs more height. |
| Destructive access actions | Regeneration and revocation can interrupt existing clients immediately. | Show a concise native confirmation with the actual consequence. Keep existing permission, certificate, scope and account validation. Empty key imports cannot submit. |
| Loading and feedback | Existing determinate transfer progress and nearby status are useful. | Retain working cached content, cancellable requests, inline feedback and distinct unavailable states. Do not replace all feedback with alerts or add fabricated success states. |
| Official Connect IQ editor | Form fields are supplied by Garmin's official WebKit editor, not generated by WristBeam. | Review the native wrapper, loading, save validation, nested navigation and unsaved-change confirmation; preserve official form behavior and origin checks. Do not claim all vendor templates were exercised offline. |

Apple documents that `titlebarAppearsTransparent` controls the background, not the existence of standard buttons, and that a full-screen window does not draw its normal title bar. Neither fact establishes the cause of the installed screenshot: [title-bar background](https://developer.apple.com/documentation/appkit/nswindow/titlebarappearstransparent), [full-screen style](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/fullscreen).

## Verification record

Local checks are static only: localization coverage, Python syntax, repository policy and diff whitespace. Native build, executable tests and rendering run exclusively in GitHub Actions. CI images use isolated synthetic data. The additional native fixture verifies real standard buttons, normal-window zoom/minimize/close/reopen and captures the AppKit frame; full-screen capability alone must not be described as a successful enter/exit test.

Status: implementation in progress; native and visual acceptance pending. No new release or installed upgrade is implied by this development branch.
